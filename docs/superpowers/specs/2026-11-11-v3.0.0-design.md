## 一、意图与「为什么」

用户原话（2026-11-11）：

> 按照你给我的建议优化打包3.0版本，尽量在风格和画面上做出不一样，在你的点之外，还有几个要点，关于批量解读，要加个保存位置的选项，解读完成后自动导出md格式，每个人一份。所有的ai解读在ai请求的时候要做好进度条展示，特别是现在有没有连接的状态，是发送不成功还是没有回复，还是在回复中tok/s是多少这样子。

拆成四件事：

1. **视觉全面重做**（用户在我给的三档中明确选了 **B档：全面重做视觉体系**）。
2. **批量解读加保存位置 + 完成后自动导出 md，每人一份**。
3. **所有 AI 请求要有真实进度条**：连接状态、是发不出去还是没回复、回复中实时速率（字/秒）。
4. **我审查 v2.5.0 时列出的问题**（P1 手动保存丢 `audience`、P2 规范文档缺受众段落、P3 若干卫生问题）。

### 为什么第 3 件事不是「加个字段」

实测 `https://www.hyai666.top/v1/chat/completions` 的流式行为：

```
status=200  content-type=text/event-stream
首个 delta 出现在 ms=2008（模型是推理型，思考阶段完全静默）
delta events=5  chars=9  totalMs=2039
```

**首个 token 要等 2 秒以上，期间界面无任何信号。** 而且「已发送 / 已连接 / 无回复 / 正在接收」四态在当前实现里**根本无法区分**——`explain()` 是一次性 `await` 响应体，中间过程完全不可观测。全库 `stream` 零命中。所以这是要把 SSE 从三条传输通道一路打通到状态区，不是加字段。

好处：**速率会是真实测量值**（累计输出字符数 ÷ 已耗时），不是伪造的百分比。单位用「字/秒」而非 tok/s——只有服务端知道真实 token 数。

## 二、目标 / 非目标 / 反目标

### 目标
- 视觉上「一眼不同」：全新配色体系、字体栅格、卡片语言、页面骨架。
- 旧观感**可切回**（保留 `classic` 皮肤），因为用户此前的验收标准建立在现有观感上。
- AI 请求全程可观测：四态 + 实时字/秒 + 已收字数 + 已耗时 + 上限剩余。
- 批量解读可选输出目录，完成后自动落盘 md，一人一份。
- 修掉我审查出的 P1/P2，它们会造成静默错误。
- 323 项测试与 29 项冒烟自检**全绿**。

### 非目标
- 不改计算内核、数据结构、`SCHEMA_VERSION`、备份格式、曼陀罗锚点。
- 不改路由表、不改 `cacheKey()` 口径（除受众已在 v2.5.0 进入）。
- 不做移动端原生 UI 重写（沿用现有响应式降级）。
- 不引入 UI 框架 / CSS 库 / 图标库（保持零新增运行时依赖）。

### 反目标（技术上成功但用户仍不满意）
- 视觉变了但**可读性下降**（对比度不足、字号变小、信息密度过载）。
- 流式导致**重复计费**或缓存键分裂。
- 批量导出**覆盖用户已有文件**，或半途失败留下一堆半截 md。
- 速率是**估算值假装成实测值**（必须来自真实 delta 时间戳）。
- 为了视觉重做把 29 项冒烟断言改掉，等于**放弃了交付自检**。

## 四、方案取舍（已与用户确认 B档）

### 4.0 ★ 审查发现的两个硬阻塞（必须先解决，否则 nova 会静默失效）

#### 阻塞 A：用户自定义样式的内联变量会压过 nova 皮肤

`applyToDom()`（`src/stores/settings.ts:300-317`）把 5 个变量以**内联样式**写在 `<html>` 上：

```js
root.style.setProperty('--center-defined-color', this.appearance.centerDefinedColor)
root.style.setProperty('--center-open-color',    this.appearance.centerOpenColor)
root.style.setProperty('--center-defined-weight', …)
root.style.setProperty('--center-open-weight',    …)
root.style.setProperty('--keyword-color',         this.appearance.keywordColor)
```

内联样式优先级**高于任何 `:root[data-skin='nova']` 规则**。而 `DEFAULTS.appearance`（`settings.ts:88-97`）写死的是 classic 的色值（`#1a1d23` / `#8a909c` / `#5b616e`）。结论：**nova 的九中心与关键字配色永远无法生效**，而这正是「一眼不同」的关键部位之一。

**解决**：新增标记字段 `appearance.styleTouched?: boolean`（默认 `false`）。
- `setStyle()` 被调用时置 `true` 并持久化；
- `applyToDom()` 仅当 `styleTouched === true` 时才写这 5 个内联变量，否则交给皮肤 CSS；
- 存量用户没有该字段 → 视为 `false` → 改用 nova 配色（他们大概率没动过；真动过的人下次在设置页改任意一项时被标记，重新拿回控制权）；
- 新增「恢复默认样式」按钮：把 `styleTouched` 置回 `false` 并清掉这 5 个内联变量。

**为什么必须显式标记**：无法用「值是否等于 DEFAULTS」推断用户意图——用户可能恰好就选了默认色，也可能从没打开过设置页。

#### 阻塞 B：若默认主题改成深色，冒烟自检会**变成空转**

`desktop/main.cjs:647-655` 的深色检查：

```js
const btn = [...document.querySelectorAll('button')]
  .find((b) => (b.getAttribute('aria-label') || '').includes('深色'))
if (btn) btn.click()
const dark = await js(`document.documentElement.dataset.theme`)
check('深色模式切换', dark === 'dark', String(dark))
```

它找的是 `aria-label` 含「深色」的按钮。若应用**启动即深色**，`AppToolbar.vue:51` 的标签会变成「切换到浅色」→ 找不到按钮 → `btn` 为 `null` → 不点击 → `dataset.theme` 本来就是 `'dark'` → **`check` 通过，但什么都没验证**。AC-3「29 项全绿」会失去意义。

**解决**：**nova 的默认明暗仍为 `light`**，深色作为一等公民的变体（而非默认）。
- 保住 AC-3 的真实性（切换仍从 light → dark，断言有效）；
- 「深色优先」的设计意图改为通过**更高对比、更重的层次**在浅色档体现，深色档做到与 classic 深色明显不同；
- 顺带避免「用户升级后界面突然变黑」的惊吓。

### 4.1 视觉体系

| 方案 | 内容 | 取舍 | 结论 |
| --- | --- | --- | --- |
| A档 | 新增一套深色优先主题，改 tokens 与组件观感，结构不动 | 差异中等、风险最低 | 用户否决（要更多） |
| **B档** | **全面重做：新配色 + 新字体栅格 + 新卡片语言 + 8 视图骨架重排** | **差异最大；必须同步维护冒烟契约，回归面最大** | **✅ 用户选定** |
| C档 | 只换配色与字体 | 达不到「尽量不一样」 | 否决 |

**B档的关键设计决策：皮肤轴与明暗轴分离。**

```
data-theme = light | dark        ← 既有轴，冒烟断言依赖，语义不变
data-skin  = classic | nova      ← 新增轴，默认 nova
```

理由：
- 冒烟断言只读 `dataset.theme`，加一条正交轴不动它。
- 用户此前所有验收（v2.3.0 页面重设计 AC-1～AC-32）建立在 classic 观感上，保留 `classic` 可随时对照与回退。
- 两轴正交 → 4 种组合（nova-light / nova-dark / classic-light / classic-dark）由同一套 CSS 变量机制输出，不需要四份样式。

**nova 的视觉语言**（与 classic 的差异必须是一眼可见的）：

| 维度 | classic（现状） | nova（新） |
| --- | --- | --- |
| 底色 | 冷灰 `#f3f5f9` | 暖墨底，深色优先；浅色档为纸感米白 |
| 主色 | 近黑 `#1a1d23` | 靛蓝主色 + 琥珀强调（数据语义三色保留） |
| 卡片 | 细边框 + 极轻阴影 | 无边框、分层投影、大圆角，靠留白分割 |
| 字体 | 系统栈，13/14px 混排 | 更紧的标题栅格 + 明确字号阶梯，数据用等宽 |
| 工具条 | 实心条 | 悬浮胶囊，滚动时收窄 |
| 人体图底板 | 青色渐变 | 深色档为深墨底 + 高对比通道；浅色档保留青色（**不做跨档突变**） |
| 动效 | 140/220ms | 更长的层级过渡，遵循 `prefers-reduced-motion` |

**人体图**：底板与通道配色随皮肤走，但**几何、闸门坐标、通道路由零改动**（那是计算与渲染契约，改动会破坏已验收的图形）。只改颜色变量与描边层次。

**★ 可行性实测（决定 B档成本的关键数据）**：扫描 `src/**/*.vue` + `*.css` 得到

```
var(--...) 使用次数 = 1549
硬编码颜色（#hex / rgb / hsl）= 215，其中 tokens.css 自身占 109
→ 组件里真正的硬编码颜色只有约 106 处，分散在 45 个文件
```

也就是说：**代码库已有约 93% 走设计令牌**。换肤主要通过 `tokens.css` + `base.css` 两个文件生效，视觉差异立刻覆盖全站；剩下约 106 处硬编码色按需逐个替换即可。这使 B档在「画面差异大」与「不失控」之间可行——不需要逐个组件重写样式。

### 4.2 流式进度

| 方案 | 内容 | 取舍 | 结论 |
| --- | --- | --- | --- |
| ① 轮询模拟 | 用定时器假装进度 | 速率是假的，违反反目标 | 否决 |
| ② 只加状态文案 | 分「已发送 / 等待 / 收到」但不流式 | 拿不到实时速率，也拿不到「正在接收」的增量感 | 不满足需求 |
| **③ 全链路 SSE 流式** | 三通道都支持 `stream:true`，主进程/原生桥把 chunk 推回渲染层，实时累计 | **工程量最大；要处理分帧、[DONE]、推理模型静默期、非流式回退** | **✅ 选此** |

**四态语义**（对应你的原话「有没有连接 / 发送不成功 / 没有回复 / 在回复中」）：

| 状态 | 触发 | 文案 |
| --- | --- | --- |
| 未连接 | 初始 / 配置校验失败 | `等待发起` / `配置未通过校验` |
| 发送不成功 | fetch/连接建立失败、DNS、TLS、被拒 | `连接失败：<原因>` + 明确「网络/跨域/Key」归类 |
| 已连接·无回复 | 连接建立但还没收到首个 delta | `已连接，等待模型开始输出（已等待 Ns）` |
| 回复中 | 收到 delta | `正在输出 · 已 N 字 · X.X 字/秒 · 耗时 Ns` |
| 已完成 | `[DONE]` | `已完成（耗时 Ns · N 字 · 平均 X.X 字/秒）` |

**「已连接」的判定必须真实**：桌面 `net.request` 的 `response` 事件、安卓 `HttpURLConnection.getResponseCode()` 返回、网页 `fetch` resolve —— 这三处才代表连接建立。绝不能靠计时器猜。

**速率实测口径**：`累计有效字符数 ÷ (now - firstDeltaAt)`，用滑动窗口平滑（最近 3 秒）。中文字符按 1 字计，不换算 token（避免假装精确）。**单位是「字/秒」而不是 tok/s**——只有服务端知道真实 token 数，字/秒是能实测的、更诚实。

**★ 禁止用百分比进度条**（改写自实测发现）：`tests/aiStatus.test.ts:73` / `:100` 明确断言单次档与完整档的 label 都不含 `%`，该测试的意图是「禁止假百分比」。流式场景下总长度未知，百分比同样是伪造的。所以进度展示走「已 N 字 · X 字/秒 · 耗时 Ns」+ 无上限的横向脉冲条（非百分比填充）。

**漂移检测（自动修正认知）**：维护 `lastDeltaAt`，若距上次 delta 超过 5 秒，追加「已 Ns 无新内容（模型可能在思考）」。这是**观测事实**，不是猜测服务端状态，符合 `useAiStatus.ts:11` 的可观测口径约束。**这条对推理模型是刚需**——实测首 delta 在 2008ms，而思考段可能更长。

**性能预算**：`useAiStatus` 已有 500ms 定时器刷新 `elapsedMs`。流式下 delta 可能每秒数十次，**不能每个 delta 都触发 Vue 响应式更新**。实现者需对「已收字数 / 速率」做节流（建议 ≤4 次/秒），并保证 delta 累积本身不丢字符。

**非流式回退**：中转站/模型若不支持 `stream:true`，必须能退回一次性请求（检测 `content-type` 非 `text/event-stream`，或响应体是完整 JSON）。回退时状态区显示「该接口不支持流式，已改用整段返回」。

### 4.3 批量保存位置 + 自动导出

### 6.1b 流式文本：决定「要」，但要节流

审查问到 §4.2 只描述了计数器、没写是否**逐字显示正文**。决定：**要显示逐字正文**。

理由：你要的是「是发送不成功还是没有回复，还是在回复中」——只给计数器看不到内容时的等待感与看到文字在长出来的等待感完全不同；而且「在回复中」这个判断，正文本身就是最强的证据。

实现要点：
- `explain()` 新增增量回调（`AiStageEvent` 现无 delta 载体，需扩一个 `onDelta?: (text: string) => void` 或新增 `AiStage` 值），**不改 `explain()` 的 `Promise<string>` 返回类型**（4 个调用点 + 大量测试依赖它）。
- `ui` 新增增量 setter（现有 `setAiContent()` 会顺带 `loading=false` 并清 error，不能复用于增量）。
- **流式期间以纯文本追加渲染，结束时再走一次 markdown 渲染**——避免每个 delta 都重新解析 markdown（`renderMarkdown` 是正则解析，逐字调用会卡）。
- 节流至 ≤4 次/秒（累计字符数仍逐字累加不丢，只是渲染节流）。
- 既有测试锁死的 B 区两个分支 `v-else-if="loading && !hasContent"` 与 `v-else-if="loading"`（`aiConcurrency.acceptance.test.ts:580-581`）**天然兼容**：首个 delta 到达后 `hasContent` 变真，自动从第一个分支切到第二个。不需要改这两个分支。
- `emit('cancel')` 必须仍恰好 3 处（:579），新增的流式取消入口**复用**既有三个分支之一，不新增第四个。

### 6.2 流式展示深度：逐路显示（用户选乙）

用户明确选择**乙：并发也逐路显示实时状态**。即批量与完整档的每个任务都要有自己的实时行（状态 + 已收字数 + 字/秒）。

#### 架构：新增 per-task 流式注册表，不动 `useAiStatus` 的单例契约

`useAiStatus` 是刻意设计的**单例单快照**，且 `applyStage` 在 `mode==='full'` 时是空操作——它是「当前这一个面板」的状态。为了不破坏这个契约（以及依赖它的 4 条断言），per-task 状态放在**新模块**：

```
src/composables/useAiStreams.ts   （新增）
  - 模块级 Map<taskKey, StreamSnapshot>
  - taskKey = `${scope}|${ref}` 或批量下的 archiveId
  - StreamSnapshot = { taskKey, label, phase, chars, charsPerSec, firstDeltaAt,
                       lastDeltaAt, startedAt, done, error }
  - begin(key,label) / delta(key,text) / finish(key,ok) / resetAll()
  - 节流：内部累计逐字不丢，对外 ≤4 次/秒 触发响应式更新
```

**为什么不复用 `useAiStatus`**：单例无法表达 N 路；硬塞会引入第二套「当前状态」，与 `aiStatus.test.ts` / `aiConcurrency.acceptance.test.ts` 的「状态唯一源」断言直接冲突。

#### 两处 per-task 界面的落点

| 场景 | 落点 | 约束 |
| --- | --- | --- |
| **跨档案批量** | `BatchReadingStatus.vue` 展开为「每份档案一行」：档案名 + 态 + 已收字数 + 字/秒 | **该文件未被任何静态断言引用**（实测确认），可自由重构；保留既有 `.dot/.bar/.act` 类以不破坏视觉连续性 |
| **完整档** | `AiReadingPanel.vue` 的 **D 区**（`report-item` 列表）就地显示「该分项正在输出」尾部预览 + 速率 | D 区有 9 条禁用项（`emit('close'/'regenerate'/'save'/'copy'/'settings')`、`doExport(`、`setAll(`、`requestRegenerate(`、`requestClose(`）→ 流式行**只能是纯展示**，不得含任何交互调用；`role="status"` 与 `class="progress-wrap"` 均必须仍恰好 1 处 |

**D 区新行的写法**（避开所有静态断言）：
- 用 `role="list"` / `role="listitem"`，**不用 `role="status"`**（否则 `:585` 的 `toHaveLength(1)` 失败）；
- 新类名如 `.stream-row` / `.stream-rate`，**不新增 `class="progress-wrap"`**（否则 `:586` 的 `toHaveLength(1)` 失败）；
- 不出现 `%`（`aiStatus.test.ts:73/:100`）；
- 不出现「进行中」（`aiConcurrency.acceptance.test.ts:584/:1034`）。

#### 完整档的「已收到内容」也要逐路可见

完整档现在只在分项完成后把 `sections` 推进 `report`，中途 D 区是骨架屏。逐路流式后：**每完成一个分项即插入列表**，进行中的那项显示尾部 2–3 行预览 + 速率。这样用户能在 46 次请求的长流程里看到「现在到哪、快不快、是不是卡住」。

#### 批量的 per-task 行与既有聚合条并存

顶层保留既有聚合条（`3/12 份 · 总耗时 · 汇总`），**新增可折叠的 per-task 明细**。理由：并发 128 时逐路展开会淹没界面；默认折叠、需要时展开，既满足「逐路可见」又不失控。
