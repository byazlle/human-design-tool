## 一、一句话说明

**这一版修的是"盘算得对不对"和"关系结论站不站得住"，不是加功能。**
最重要的一项：人类图罗盘的起始锚点此前偏了 2′30″，所有盘在边界附近的爻位可能错一格；
本版按 Jovian 官方口径修正，并让老档案自动重算。因此**同一出生信息在本版与上一版可能得到不同的
人生角色或交叉角度** —— 这是修正，不是回归。

## 二、改动清单

### 2.1 P0：计算正确性

| 项 | 内容 | 依据 | 影响 |
| --- | --- | --- | --- |
| 曼陀罗锚点 | `MANDALA_OFFSET` `29.8333°` → **`29.875°`**（Gate 41 起于宝瓶 2°00′ = 302.000°） | Jovian 公布的两个 Rave New Year 时刻反算：2024-01-22 13:18 UTC、2026-01-22 00:54 UTC，太阳黄经 302.0002° | 约 4.4% 激活点爻位、0.74% 闸门可能变化；爻变会连带人生角色与交叉角度 |

**如何自证**：`node scripts/check-mandala-anchor.mjs`
- 旧实现：两个官方时刻 → `Gate 60.6`
- 修正后：两个官方时刻 → `Gate 41.1`

### 2.2 P1：数据可信与流程拦截

| 项 | 改动 | 之前会发生什么 |
| --- | --- | --- |
| 算法版本戳 | `BodyGraph.meta.engineVersion`，启动比对 + 自动重算 | 算法修好了，老档案仍显示旧结果，且无提示 |
| 合盘同人拦截 | 引擎断言 + 页面空态 | 手改 URL `/composite/X/X` 可"与自己合盘"，全部通道判为"同伴"，AI 输出"高度同频" |
| 导入校验 | 出生字段逐项校验 + 跳过清单 | `{month:13, hour:25}` 被 `Date.UTC` 静默滚动成另一个日期，产出错误盘 |
| 数据损坏保护 | 读取失败备份原文 + 顶部警示 | 档案库"凭空清空"，下一次写入覆盖损坏内容 |
| 校验下沉 | `computeChart()` 入口校验 | 导入 / 手改 URL / 未来分享链接可绕过 UI 校验 |
| 移除 `channelKey()` | 改为严格查表的 `channelKeyOf()` | 任意两整数可造出"看起来合法"的通道 key（当前无调用点，属隐患） |

### 2.3 合盘口径修正（用户可感知）

| 改动 | 说明 |
| --- | --- |
| **删除**"合图的类型 / 权威 / 轮回交叉" | 类型与权威属个体气场属性；轮回交叉由个体的人格/设计太阳-地球四闸门构成，两人叠加不存在"第三个交叉" |
| **新增**"中心四象限" | 双方都定义 / 仅 A / 仅 B / 双方都开放。原来只给并集，看不出"谁在影响谁" |
| **新增**"关系主题" | 离线五段结论：结构概览、影响力方向、共鸣区、共同放大区、连接方式。**未配置 AI 也能读到关系结论** |
| 四类连接通道 | 保留（电磁 / 同伴 / 主导 / 妥协），判定逻辑未改 |
| AI 提示词 | 同步移除合图类型/权威/交叉，改为四象限 + 口径约束 |

### 2.4 内容修正

- 显示者权威：删除"心智投影型"（显示者必有马达连喉，权威不可能落在心智层）。
- 投射者机制：洞察改为"开放中心接收并放大环境能量"，不再归因于喉咙连接。
- 12 处中英混排/错字（`接纳之 gate`、`完成 cycles`、`Spirit / 自由`、`资源的 王 / 统领` 等）。
- 轮回交叉"人生第三阶段"改为按角色分支：仅含第 6 爻的角色适用三阶段结构。
- 删除交叉文案中的"凯龙周期"（凯龙不属 13 体）。
- 选中 3 份时提示由"请再选择一份"改为"合盘只能选 2 份，当前已选 N 份"。

## 三、对用户的影响（运营口径）

| 用户类型 | 影响 | 建议话术 |
| --- | --- | --- |
| 新用户 | 无感知 | — |
| 老用户（盘面未变） | 无感知，仅启动时重算 | "打开即最新" |
| 老用户（角色/交叉变了） | 会觉得"我的盘变了" | 主动公告：**我们修正了罗盘起始锚点**，仅边界附近会变；新结果与 Jovian 官方口径一致 |
| 用 AI 解读过的用户 | 旧解读基于旧盘，可能与新盘不符 | 提示"AI 解读缓存仍为旧结果，可清空后重新生成" |
| 合盘用户 | 少了一块"你们的类型" | 说明：**关系不是一个人，没有类型**；改为"影响力方向 + 关系主题"，信息量更大 |

> ⚠️ 建议发布时同步放一条公告，把"2′30″ → 会改变什么"讲清楚，否则容易被误读为"软件算错了"。

## 五、构建与产物

| 步骤 | 命令 | 结果 |
| --- | --- | --- |
| 前端 | `npm run build` | `dist/` |
| Windows 安装包 | `python scripts/build-exe.py` | `release/desktop/HumanDesign-Setup-1.2.0.exe`，77 MB |
| Android APK | `python scripts/build-apk.py` | `release/android/HumanDesign-1.2.0.apk`，508 KB，v2/v3 签名已验证 |

**校验和（SHA-256）**

```
3d6ef45eb01f7b54ced0598036bbc14cb32fa25998d460b56a1f2e0af947bbda  HumanDesign-Setup-1.2.0.exe
82825c27ea7a964e5005799b6d4f7ad1633c78af76d160cd744246feb884d211  HumanDesign-1.2.0.apk
```

版本一致性：`package.json` = `desktop/package.json` = **APK 清单 `versionName`/`versionCode`** = 产物文件名 = `1.2.0`。

> **打包环节顺手修掉的一个问题**：首次打 APK 时文件名是 1.2.0，但清单里仍是 `1.0.1 / 11` ——
> 原因是 `aapt2 link` 的 `--version-code` / `--version-name` **只在清单缺少该属性时生效**，
> 而本仓库 `AndroidManifest.xml` 是静态写死的，参数被静默忽略。
> 已在 `scripts/build-apk.py` 中改为「按 package.json 生成补丁清单再链接」，`versionCode` 由语义化版本推导
> （`major*10000 + minor*100 + patch` = 10200），并去掉重复的 `--version-code` 参数。
