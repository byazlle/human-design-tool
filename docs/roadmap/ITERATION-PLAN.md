# 产品迭代计划 v2（表达可懂性驱动版）

> 基准：2026-11-20 · v3.6.0 + 提示词内容修订 4.1
> **本版替换旧的迭代计划（已删除）**。新版的根本变化：把用户反馈的「看不懂 / 似懂非懂」从"提示词措辞问题"上升为**贯穿全产品的核心议题**——因为根因不止在提示词，还在作为素材的离线释义库与静态文案层。
> 配套：[ROADMAP.md](ROADMAP.md)（战略与指标）· [DEV-ITERATION-PLAN.md](DEV-ITERATION-PLAN.md)（开发执行）· [CONFIRM.md](CONFIRM.md)（待你确认）· [DECISIONS.md](DECISIONS.md)（口径留痕）

## 0. 为什么重做这份计划

### 0.1 触发：一个被误判的问题

v3.4 做过"白话口径重写"，v4.0 做过"表达风格双层"，v4.1（本次）加了 few-shot 对照和新规则。但用户反馈始终是同一句：**"就算大白话也看不懂，似懂非懂。"**

连续三次修提示词都没根治，说明**问题不在提示词层**。做根因分析后定位到四个源头：

| 源头 | 证据 | 性质 |
| --- | --- | --- |
| ① 提示词只有禁令 | 旧风格段全是"禁止玄词/长句/假翻译"，没有正面范式 | 已修（v4.1 few-shot） |
| ② **离线释义素材抽象** | `interpretations.ts` 254 行、`gateInsight.ts` 89 行、`destinyText.ts` 187 行、`typeDetail.ts` 134 行——64 闸门 / 36 通道 / 9 中心 / 5 类型 / 7 权威的静态文案本身是抽象话；AI 拿它当素材，再口语化也会被带偏 | **未修 · 新计划核心** |
| ③ **术语三套叫法混用** | 意识/无意识、显意识/潜意识、人格/设计并存（C7）；「开放的通道」与「开放中心」撞词（C11） | 未修 · 依赖 CONFIRM C 组 |
| ④ **没有可懂性验收** | 全库测试断言的是"逐字一致 / 字段齐全 / 字数区间"，**没有任何一条测"用户能不能看懂"** | **未修 · 新计划核心** |

### 0.2 结论：表达可懂性是一个产品系统，不是一个提示词参数

> 新计划的第一主题从"堆 AI 功能"改为 **"全站表达可懂性工程"**：
> 提示词（v4.1）→ 离线释义素材 → 术语统一 → 可懂性验收 → 用户验证闭环。
> 计算内核仍然冻结——"看不懂"是表达问题，不是算错问题，不能拿内核开刀。

### 0.3 本版与旧版的具体差异

| 维度 | 旧版 | 新版 |
| --- | --- | --- |
| 第一主题 | 口径收口 + 度量 | **表达可懂性**（口径收口降为并列主题） |
| 度量定位 | 北极星是目标 | 北极星仍是目标，但**新增"可懂性"作为驱动指标** |
| 离线释义 | 完全没提 | **独占 I-2 一个迭代**（审计 + 白话化 + 测试） |
| 术语统一 | I-6 收尾 | 提前到 I-2，与释义一起做（同一批文案） |
| 验收方式 | 通用 DoD | **新增"可懂性检查表"**：每条释义必须过"三问" |
| 用户验证 | 无 | 新增 I-4 "拿真实用户的问题来验证是否真的看懂" |

## 1. 北极星与指标（在旧版基础上增补）

- **北极星**：WIKC = 每周完成「解读 → 保存 / 导出」闭环的活跃档案数（口径待 CONFIRM B2 确认）。
- **新增驱动指标：可懂性达标率**
  - 定义：随机抽取 N 条 AI 输出 + 离线释义，按第 5 节「可懂性检查表」逐条判定，达标条数 ÷ 抽检条数。
  - 基线：未测（I-1 先做一次抽检建立基线）。
  - 目标：I-2 结束后 ≥ 80%；I-4 用真实用户反馈校准。
- 其余驱动 / 健康指标见 [ROADMAP 第 6 节](ROADMAP.md#6-指标体系north-star--驱动--健康)，不变。

### I-2 · 离线释义白话化（2026-12-07 → 12-18 · v3.8.0）★ 新版核心迭代

**为什么**：这是"看不懂"最被低估的根因。AI 提示词已经升级到 4.1，但如果它拿到的素材还是"你有持续不断的创造性输出，作品本身就是你的名片"这类抽象话，生成结果仍会飘。素材改了，提示词的效果才落得了地。

**目标**：把 AI 的"原料"从抽象话改成生活话，并统一术语。

**范围**
- Must：审计并白话化以下静态文案（逐条过第 5 节检查表）：
  - `src/services/interpretations.ts`：`GATE_TEXT`（64×2 段 defined/open）、`CHANNEL_TEXT`（36 条）、`CENTER_TEXT`（9×2）、`TYPE_TEXT`（5 类型七段）、`AUTHORITY_TEXT`（7 权威）
  - `src/services/gateInsight.ts`：64×4 字段（trait/growth/grounding/drive）
  - `src/services/destinyText.ts`：4 类人生轨迹分层文本
  - `src/services/typeDetail.ts`：5 类型详解
- Must：术语统一——按 CONFIRM C7 结论统一"意识两侧"叫法，按 C11 给「开放的通道」改名；产出全站术语对照表 `docs/GLOSSARY.md`。
- Must：新增 `tests/readability.test.ts` 正式版——对**离线释义**断言禁用解释词、句子长度上限、每条含可观察场景锚点。
- Should：用 I-1 抽检出的不达标样例定向重写，不是全库无差别重写（省时间、保风格一致性）。
- Non-goals：**不改任何数值 / 判定 / 计算**；不改提示词正文（v4.1 已定）；不动 UI 布局。

**验收**
- 可懂性达标率 ≥ 80%（基线对比）；
- 术语对照表覆盖 5 处抽查点（档案库 / 单盘 / 合盘 / 设置 / AI 面板）无混用；
- 测试全绿，且新增断言在故意塞入抽象话时会变红。

**依赖与风险**：依赖 I-1 基线报告定位问题样例；依赖 CONFIRM C 组术语结论（未确认则只出对照表、不改代码）。风险：文案量大（约 700+ 条），用"抽检定向重写 + 规则兜底"而非逐字手写全部，控制工作量。

## 5. 可懂性检查表（本版新增 · 贯穿 I-1/I-2/I-4）

> 每条离线释义与 AI 输出按此逐条判定。这是"看不懂"从主观抱怨变成可测指标的钥匙。
> 来源：v4.1 提示词的三条规则 + 用户三个症状（抽象套抽象 / 术语代号绕 / 例子太假）。

**三问法**（任一条答"否"即判不达标）：

1. **有画面吗？** 这条描述里有没有"谁 / 什么场合 / 身上什么反应"？只有抽象判断（模式、能量、制约、放大、整合、课题）没有画面 → 不达标。
2. **不绕吗？** 闸门号 / 通道号 / 术语有没有当句子主语或放段首？有没有用抽象词解释抽象词？有 → 不达标。
3. **对得上吗？** 例子是"换谁都成立"的空话（如"你在工作中会遇到挑战"），还是带具体时机（下次开会 / 被临时改约 / 晚上躺床上）？前者 → 不达标。

**机械可判定项**（用于 `tests/readability.test.ts` 自动断言）：
- 禁用解释词表：能量 / 频率 / 磁场 / 共振 / 天命 / 业力 / 高维 / 模式 / 制约 / 放大 / 整合 / 课题
- 单句长度上限（建议 ≤ 45 字，超出须拆句）
- 每条 defined/open 文本至少含一个具体场景锚点（可枚举词表命中）

**人工判定项**（抽检打分）：三问法整体判定，I-1 基线 30 条、I-4 复盘抽样。

## 6. 通用非目标与发布纪律

- **所有迭代共同非目标**：不改计算内核 / 曼陀罗锚点 / 通道判定 / 合盘口径 / `SCHEMA_VERSION`（除非 CONFIRM A 组明确勾"改动"）。
- 改提示词必同步：跑 `node scripts/sync-prompt-spec.mjs` + 升 `PROMPT_VERSION` + 改 4 处测试断言。
- 改释义文案不改版本号（内容数据，非提示词 / 内核），但需更新 CHANGELOG 与可懂性报告。
- 推送通道 curl / Node fetch 会交替失效，发布前探测；CI tag 四 job 是唯一权威产物。
