## 1.【意图分析】

**用户到底要什么**：你已经让架构师把 v3.8.0 的目标和效果规划好了（就是 `ITERATION-v3.8.0.md`），现在缺的是「把规划翻译成能直接开干的提示词和内容」，交给开发团队落地。所以本交付不是再设计一遍 v3.8，而是把架构师设计**转译成可复制、可执行、带约束、带验收的操作提示词**。

**原始提示词的缺口**（增强前）：
| 缺口 | 表现 | 本包如何补 |
| --- | --- | --- |

**隐含前提**：架构师文档是权威输入，本包只做转译 + 结构化，不新增业务口径、不改计算内核、不改提示词版本。

## 3.【约束清单】

### 3.1 硬约束（可机器检验，违反即打回）

- **H1** 单句 ≤ 45 字；每条至少命中 1 个场景锚点；12 禁用词零命中：能量 / 频率 / 磁场 / 共振 / 天命 / 业力 / 高维 / 模式 / 制约 / 放大 / 整合 / 课题。
- **H2** 条目数只增不减：8 类载体合计 524 条，不得靠删条目达标；改好一条从 `readability-baseline.json` 的 failing 集合删一条。
- **H3** 术语与编号不当主语/段首，放句尾括号（如「……（闸门 57、脾中心）」）；全篇只括注一次。
- **H4** 内核零改动：`ENGINE_VERSION` 保持 `2.0.0+mandala.29.875`；不改任何数值/判定/计算。
- **H5** 产品提示词零改动：`PROMPT_VERSION` 保持 `4.2`；不改 `aiPrompt.ts` 12 段；不跑 sync 脚本；不改 `AI-PROMPT-v4.0.md`。
- **H6** 不改 UI / 路由 / 数据结构 / 类型签名；不改 `docs/review/` 历史审查文档。
- **H7** 分批纪律：前一批未过 L1+L2+L3，不得开下一批；每批提交到 `dev/DEV-702-batch-N` 分支。
- **H8** 验证门槛：L1 = 524/524；L2 每类抽检 ≥5 条、合计 ≥90%、无"完全看不懂"；L3 每人 ≥3/10。
- **H9** 全量回归：`npm test` ≥544 项全绿、`npm run typecheck` 0、`npm run build` 通过；产品版本升 `3.8.0`（根 `package.json` 单一来源）；CI 四 job 绿。

### 3.2 软约束（风格与取舍偏好）

- **S1** 语气：第二人称"你"，像朋友指给你看一件事，不像说明书，不像算命。
- **S2** 取舍：宁可少说一个道理，也要留一个具体画面；画面写不出来就删那句，不要凑抽象词。
- **S3** 例子从盘面取值、带具体时机 + 自检问题，不用"比如你工作中……"这类放谁身上都成立的假例子。
- **S4** 术语中文口径沿用项目现行（人格/设计、闸门/通道编号），不发明新译名。

```

你是 HumanDesignTool 的「离线释义改写专员」。任务是把项目里抽象的离线释义文案，

- gateInsight（256 条，4 字段×64，达标率最低优先改）：trait 口语化；
  growth / grounding / drive 各给一个可执行动作。
- typeDetail（55 条，已较好）：每段开头给场景，再接解释，改动量小。
- destinyText（19 条，达标率最低）：四类轨迹每段补具体时间点与可验证信号。

  手心 / 身体 / 第一反应 / 本能 / 放松 / 收紧 / 开口 / 沉默 / 停下 / 记下来 /

   高维 / 模式 / 制约 / 放大 / 整合 / 课题。命中即标出。
3. 场景锚点：每条至少命中 1 个，且必须是这 52 词表内的词：
   开会 / 被问 / 被邀请 / 被改约 / 临时 / 下次 / 早上 / 晚上 / 睡前 / 半夜 / 周末 /
   每天 / 每周 / 每年 / 每季度 / 争执 / 争吵 / 道歉 / 吃饭 / 做饭 / 走路 / 通勤 /
   排队 / 加班 / 深夜 / 独处 / 休息 / 腹部 / 肚子 / 呼吸 / 心跳 / 肩膀 / 胃 /
   手心 / 身体 / 第一反应 / 本能 / 放松 / 收紧 / 开口 / 沉默 / 停下 / 记下来 /
   写下来 / 记录 / 试一次 / 三秒 / 10 秒 / 28 天 / 问自己 / 观察 / 练习。
   无锚点或用了表外自造词，都标出。
4. 术语位置：编号/术语是否在句尾括号内、全篇只括注一次？当主语或段首即标出。
5. 锚点堆砌：一句话 ≥3 个锚点且语义不通？标出（L2 会判"不绕"不过）。
6. 条目数：本批条数是否与派发时一致？少一条即停止提交。
7. 假例子：是否出现"比如你工作中……"这类放谁身上都成立的例子？标出。

# 输出格式
| 条目 ID | 句长OK? | 禁用词命中? | 有锚点? | 术语位置OK? | 结论(通过/退回) | 问题说明 |
末行给出：本批共 N 条，通过 X 条，退回 Y 条；Y>0 则结论为"退回 P1 重改"。

# 说明
本预检是人工自查，不能替代 tests/readability.test.ts 的自动 L1。
预检通过后仍须 CI 自动扫描，两者都过才算 L1 通过。

### P3 · L2 双盲评审打分提示词（给 2 名评审）

```
# 角色
你是 v3.8.0 的 L2 盲审评审。共 2 名评审：1 名懂产品、1 名不懂人类图。
两人背对背独立打分，打分期间不得交流。

# 输入
盲审包：从每类随机抽 5 条（8 类 → 40 条），已去掉条目 ID 与来源文件名，
只留文本，打乱顺序编号 1–40。

# 打分方法（三问法，逐条）
对每条 1–40 判断三问是否全过：
- 有画面：能否读出谁 / 什么场合 / 做了什么 / 身上什么反应？
- 不绕：有没有编号/术语当主语、抽象词解释抽象词、锚点堆砌？
- 对得上：例子有没有具体时机 + 自检问题，而不是换谁都成立？
三问全过 → ✅；任一不过 → ❌，并写一句不达标原因。
特别地：若你读完后"完全看不懂在说什么"，标 ⚠ 完全看不懂（这是硬打回项）。

# 防脑补纪律（关键）
- 懂产品的评审：不要因为你知道这条来自哪个闸门就自动脑补它的含义，只看字面。
- 不懂人类图的评审：不要去猜术语，你就按普通读者的真实反应判——
  看不懂就是看不懂，这正是你的价值。
- 只看文本本身，不查原文、不查 ID、不问同事。

# 输出格式
| 盲审编号 | ✅/❌/⚠ | 不达标原因（一句） |
末行给出：本包 40 条，✅ X 条（X/40 = 达标率），❌ Y 条，⚠ 完全看不懂 Z 条。

# 判定门槛（由组织者汇总两人结果）
- 每类抽检 ≥5 条、合计达标率 ≥90%、且无任何"完全看不懂"→ L2 通过。
- 两人均判 ✅ 才计该条达标；有分歧的条目进入共识会讨论。
- 分歧 >5 条说明标准表述不清，先修标准再审，不要硬凑结论。
```

### P4 · L3 真实试读组织与判定提示词（给试读组织者）

```
# 角色
你是 v3.8.0 的 L3 真实试读组织者。目标：验证不懂人类图的普通人能否
从改写后的文案里复述出可执行观察。

# 组织步骤
1. 找 3 名不懂人类图的普通人（家人 / 同事 / 朋友即可），
   不要找熟悉本项目的人。
2. 给每人随机 10 条改写后的释义，只给文本。
3. 不给任何人类图背景解释，不提示答案。否则测的是"解释得好"，
   不是"文本本身清楚"。

# 给试读者的引导语（逐字使用）
"这里是 10 句话。请每一句都用你自己的话回答两个问题：
 ① 这条在说我什么？ ② 我该留意什么？
不用猜术语，就像别人当面跟你说这句话你会怎么理解，就怎么说。"

# 判定标准
- 能复述出"具体场景 + 自己的反应"→ 算理解。
- 只复述抽象词（如"说我很有能量""说我直觉强"）→ 算未理解。

# 输出格式（每人一份）
| 条目序号 | 试读者复述（原话） | 理解?（是/否） | 判据（场景+反应 / 仅抽象词） |
末行给出：该试读者理解 X/10；X≥3 则该人通过。

# 总判定与打回
- 3 人每人 ≥3/10 → L3 通过。
- 任一人 <3/10 → L3 不过，整批打回；把未理解的原文条目列为重点重改对象，
  连同复述原话一起交给 P5。
```

### P5 · 打回单生成与重改提示词（给组织者 + 改写者）

```
# 角色
你是 v3.8.0 的「打回协调员」。任一验证关卡不过时，用本提示词生成打回单，
并指导改写者在限定范围内重改。

# 输入
- 不达标关卡：L1 / L2 / L3
- 触发条件与数值（见下表）
- 不达标条目清单（ID + 原文 + 原因 + 复述原话如有）
- 当前是第几轮重改（1 / 2 / 3）

  | 条目 ID | 原文 | 不达标原因 | 修改方向建议 |

## 6. 实施说明（何时用、如何调参）

- **开工顺序**：P6（工程搭基线/CI/版本）与 P1（改写）可并行；但每批改写提交后必须按
  P2 → L1 → P3 → P4 →（不过则 P5）单向推进，不得跳级。
- **批次顺序**：先批次 1（gateInsight 256 条，达标率最低）+ 批次 2（destinyText 19 条），
  再 GATE_TEXT、其余；前批未验收不开下批。
- **调参建议**：
  - 若 P1 产出仍偏抽象：优先加大 few-shot 的"反例→正例"对照，而不是追加禁用词——
    历史证明"只加禁令"无效（v3.4/v4.0/v4.1 三次教训）。
  - 若 L2 分歧 >5 条：先修"三问法"标准表述再审，不要靠多次投票凑 90%。
  - 若 L3 反复不过：问题多在"例子不具体"，回到 P1 要求补"具体时机 + 自检问题"。
- **语言/口径**：全文简体中文；术语中文沿用项目现行译名，编号格式沿用 `闸门 57`/`通道 20-34`。
- **专业裁定**：按决策 D4，第 3 轮不达标时执行层"冻结批次 + 提交打回单与 3 轮记录"即完成阶段动作；
  最终如何放宽标准、涉及业务口径的裁定，建议由项目所有者 / 具备资质人员判断，执行层不自行决定，也不空等。
