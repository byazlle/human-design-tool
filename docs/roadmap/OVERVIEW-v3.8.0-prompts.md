# 交付概览 · v3.8.0 执行提示词包（最终可执行版）

**日期**：2026-11-20
**主交付物**：`docs/roadmap/DEV-PROMPTS-v3.8.0.md`

## 我做了什么

你手上的架构师规划（`ITERATION-v3.8.0.md`）写清了"要做什么、达到什么效果"，但它是规划文档，不是能直接开干的操作指令。我把它**转译成一套可直接复制执行的提示词包**，并把所有需要拍板的事项**全部给出默认决策**——开发拿去即可开工，无需再等任何人。

按「提示词增强专家」五步模板完成：

1. **意图分析**——定位原始需求缺口（执行者不明、输入输出不明、约束散落、闭环缺失、工程侧空白）。
2. **上下文补全**——提取架构师文档 15+ 项已确认事实；把 5 个原待确认项全部拍板为默认决策（D1–D5）。
3. **约束清单**——9 条硬约束（H1–H9，可机器检验）+ 4 条软约束（S1–S4）。
4. **增强后提示词**——**7 份自包含提示词**：
   - P0 真实 ID 批次派发清单（给执行者/负责人）
   - P1 离线释义改写执行（给改写者）
   - P2 提交前机械预检（给改写者）
   - P3 L2 双盲评审打分（给 2 名评审）
   - P4 L3 真实试读组织（给组织者）
   - P5 打回单生成与重改（给组织者 + 改写者）
   - P6 工程实现总控（给开发工程师）
5. **验收标准**——7 条标准（A1–A7）用于判断"本次增强是否有效"。
6. **实施说明**——开工顺序、批次顺序、调参建议、口径与裁定提醒。

## 关键决策

- **全部拍板，零阻塞**：原 5 个待确认项（人选 / 执行方式 / 工具 / 升级决策 / UI 提示）全部给了默认决策（D1–D5）。L2/L3 人选由团队就近指派；改写用"AI 生成初稿 + 人工过 + 预检"；不做工具先手工；第 3 轮不达标则"冻结+提交材料"即完成阶段动作；不加 UI 提示。
- **口径隔离**：反复强调本包是"执行指令"，不是产品运行时提示词——不改 `aiPrompt.ts`、不动 `PROMPT_VERSION`（保持 4.2）。这是最容易踩的坑：v3.8 改的是离线释义**数据**，不是提示词**规则**。
- **闭环完整**：不只给"改写"提示词，补齐了盲审、试读、打回、重改，把架构师的"三级验证 + 打回机制"变成每关可执行的动作。
- **数据对齐真实基线**：条数（524/449）、锚点表（52 词）、ID 命名、各分类失败分布，全部取自 `tests/fixtures/readability-baseline.json` 实测，不在提示词里另造口径。P0 派发清单按真实 ID 前缀展开。
- **不臆造**：没有编造任何文案或业务口径；需人裁定的点已明确标注并给出处理路径。

## 开发现在就能做的事

1. 按 **P0** 领批次 1（insight 228 条不达标）和批次 2（destiny 18 条）——这两个是 P0 优先、量最小/最该先啃。
2. **P6** 与改写并行：确认基线测试规则、搭流程、版本升 3.8.0。
3. 每批改完按 P2 → L1 → P3 → P4 单向推进，不过走 P5。

## 唯一仍需所有者出面的场景

仅在"某批次真的打到第 3 轮仍不达标"时（D4）：执行层会冻结该批次并提交打回单 + 3 轮记录，由所有者决定放宽/换策略/保留原文。这是产品裁定，建议由具备资质人员判断——但执行层在此之前不会因为等它而停摆。
