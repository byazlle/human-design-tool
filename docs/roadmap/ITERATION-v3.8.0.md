# 迭代计划 v3.8.0 · 让每一条解读"大家都看得懂"

> 基准：v3.7.0（2026-11-20）· 提示词 4.2 · 可懂性基线 14.3%
> **本迭代的唯一目标**：把用户说的"似懂非懂"彻底做掉——不是改提示词，而是把 AI 拿来当素材的 524 条离线释义，逐条改到"读完能说出这是自己哪件事"。
> **本迭代的硬机制**：三级验证 + **不达标必须打回重改**，直到过线；不允许"改完就算完成"。
> 配套：[ITERATION-PLAN.md](ITERATION-PLAN.md)（产品 v2 总计划）· [DEV-ITERATION-PLAN.md](DEV-ITERATION-PLAN.md)（DEV-701/702/703）· [可懂性基线](../VERIFY-可懂性-基线.md) · [readability.test.ts](../../tests/readability.test.ts)

---

## 1. Why：为什么是这个迭代、为什么必须带打回机制

### 1.1 已经用数据证明的事实

| 证据 | 数值 | 出处 |
| --- | --- | --- |
| 提示词正面样例达标率 | 6/8（75%），4.2 已修到全达标 | 基线报告 §3.2 / CHANGELOG 4.2 |
| 离线释义机械达标率 | **75/524 = 14.3%** | 基线报告 §2 |
| 离线释义人工抽检 | **0/15 达标** | 基线报告 §3.1 |
| 失败主因 | 无场景锚点 436 条（占不达标 97%） | 基线报告 §2 |

**结论**：问题不在提示词（已修完），在素材。素材不修，AI 再口语也会被带偏——这就是"似懂非懂"的真正来源。

### 1.2 为什么要强制打回

过去三次"改完就说好了"（v3.4 白话 / v4.0 分层 / v4.1 few-shot）都没根治，共同原因：**没有验证闭环**。改的人自己判断"应该懂了"，没有客观门槛、没有打回机制、没有第二双眼睛。

本迭代把"改完"和"改好"分开：**改完只是提交，过三级验证才算完成；任一级不过，退回重改，且不允许带病进入下一批。**

## 2. 目标与成功定义

### 2.1 目标（一句话）

> 让 524 条离线释义中的每一条，都达到"读完能说出这是自己哪件事"——不是抽象话，是有画面、不绕、能对上号的生活语言。

### 2.2 成功定义（DoD，全部满足才算本迭代完成）

| 指标 | 起点 | 门槛 | 测量方式 |
| --- | --- | --- | --- |
| 机械达标率 | 14.3%（75/524） | **100%（524/524）** | `readability.test.ts` 全量扫描 |
| 人工三问抽检达标率 | 0/15 | **≥ 90%（每类抽检 ≥5 条）** | 盲审团按 §4.2 打分 |
| 基线快照 | 449 条不达标 | **清空（0 条不达标）** | `readability-baseline.json` 不达标集合为空 |
| 真实用户验证（I-4 或本迭代末） | 无数据 | **≥ 3 名不懂人类图的人，各能复述出 ≥3 条可执行观察** | §4.4 试读记录 |
| 回归 | 基线 | 测试只增不减（≥544 项）、构建通过、内核零改动 | 全量验证 |

> **为什么机械门槛设 100% 而不是 80%**：机械项（禁用词 / 45 字 / 场景锚点）是客观可判定的，留 20% 不达标等于把"看不懂"合法化。人工项允许 90% 是因为主观判定有灰度。

## 3. 修改方向与框架（怎么改才算对）

### 3.1 三条铁律（源自三问法）

| # | 铁律 | 反例（现在的问题） | 正例（要改成的样子） |
| --- | --- | --- | --- |
| 1 | **有画面**：谁 / 什么场合 / 做了什么 / 身上什么反应 | "你有持续不断的创造性输出，作品本身就是你的名片。" | "你脑子里冒出一个想法就想马上做出来，做的时候饭都忘了吃；被人打断时会明显烦躁。" |
| 2 | **不绕**：编号 / 术语不当主语，不用抽象词解释抽象词 | "闸门 57 给你直觉，脾中心开放让你容易焦虑。" | "你常突然『就是觉得不对』，说不出理由但事后常被你猜中；人多事乱时这准头会飘，你开始反复确认。（闸门 57、脾中心）" |
| 3 | **对得上**：例子带具体时机 + 自检问题，不是换谁都成立 | "你拥有独特的洞察力与稳定的判断基准。" | "下次开会前你会先在心里过一遍要说的话——回想最近一次，是不是这样？" |

### 3.2 改写公式（每条释义都要套）

```
原抽象结论
  → 什么时候（下次开会 / 被临时改约 / 晚上躺床上 / 截止前一天）
  → 你做了什么 / 身上什么反应（手心发热 / 忍不住接话 / 心里发紧 / 停不下来）
  → 一句自检问题（回想上一次……是不是这样？）
  → 术语与编号放句尾括号（人类图里这叫 XX / 通道 20-34）
```

### 3.3 分类型改写框架（不同载体改法不同）

| 载体 | 条数 | 改写重点 | 特别说明 |
| --- | --- | --- | --- |
| `interpretations.ts` GATE_TEXT | 128（64×2） | defined/open 各给一个"什么时候 + 反应"的生活镜头 | 关键词行可保留术语，正文必须口语 |
| 同上 CHANNEL_TEXT | 36 | 写成"两股劲碰到一起时会发生什么"，不要分述两端 | 通道是关系，不是两个闸门的叠加 |
| 同上 CENTER_TEXT | 18（9×2） | defined/open 用"这个中心在你身上是亮还是空，日常表现为……" | 禁"中心是亮的"这类隐喻（4.2 已立规矩） |
| 同上 TYPE_TEXT / AUTHORITY_TEXT | 5 + 7 | 类型七段 / 权威 short+desc 各补一个决策场景 | 权威尤其要写"做决定时怎么分辨" |
| `gateInsight.ts` 4 字段 × 64 | 256 | trait 口语化，growth/grounding/drive 各给一个可执行动作 | 这是达标率最低的类别（11%），优先批量改 |
| `typeDetail.ts` | 55 | 每段开头给场景，再接解释 | 类型详解已较好（35%），改动量小 |
| `destinyText.ts` | 19 | 四类轨迹每段补具体时间点与可验证信号 | 达标率最低（5%），需重点重写 |
| `typeDetail.ts` / 其他 | 剩余 | 按三问法逐条过 | — |

### 3.4 明确不改什么（Non-goals）

- 不改任何数值、判定、计算内核（`ENGINE_VERSION` 不动）
- 不改 12 段提示词结构与正文（`PROMPT_VERSION` 保持 4.2，除非抽检证明规则本身有误——那走 PROMPT-1 单独流程）
- 不改 UI 布局 / 路由 / 数据结构 / 类型签名
- 不改 `docs/review/` 历史审查文档（审计语境）
- **不为了达标而删条目**——达标率必须靠改写提升，不靠减少素材

## 4. 验证标准与流程（核心章节）

### 4.1 三级验证关卡

```
[L1 机械扫描] ──过──> [L2 人工盲审] ──过──> [L3 真实试读] ──过──> 该批验收
      │                     │                     │
      └─不过→打回重改        └─不过→打回重改        └─不过→打回重改
```

| 关卡 | 测什么 | 谁执行 | 通过线 | 产物 |
| --- | --- | --- | --- | --- |
| **L1 机械** | 禁用词 / 单句 ≤45 字 / 场景锚点 / 条目数不变 | `readability.test.ts` 自动 | 524/524 达标，且条目数不少 | 测试输出 |
| **L2 人工盲审** | 三问法：有画面 / 不绕 / 对得上 | 2 名评审（1 名懂产品 + 1 名不懂人类图），**背对背独立打分** | 每类抽检 ≥5 条，合计 ≥90% 达标，且无一条"完全看不懂" | 盲审打分表 |
| **L3 真实试读** | 不懂人类图的人能否复述出可执行观察 | 3 名试读者（非项目成员） | 每人从随机 10 条中复述 ≥3 条"这是什么意思 / 我该留意什么" | 试读记录 |

#### L1 机械规则（已实现，直接用）

- 禁用解释词 12 个：能量 / 频率 / 磁场 / 共振 / 天命 / 业力 / 高维 / 模式 / 制约 / 放大 / 整合 / 课题
- 单句 ≤ 45 字
- 每条至少命中一个场景锚点（开会 / 被问 / 被邀请 / 被改约 / 临时 / 手心 / 腹部 / 下次 / 睡前 …）
- 基线快照"只减不增"：改好一条就从 `readability-baseline.json` 删一条，不许放宽规则

#### L2 盲审操作细则

1. **盲审包生成**：从每类随机抽 5 条（共 8 类 → 40 条），去掉条目 ID 与来源文件名，只留文本，打乱顺序编号 1–40。
2. **独立打分**：两名评审各自按三问法逐条打 ✅/❌，并写一句不达标原因，**评审之间不得交流**。
3. **共识会**：只对分歧条目讨论；分歧 >5 条说明标准表述不清，先修标准再审。
4. **判定**：两人均判 ✅ 才算达标；达标率 ≥90%。

#### L3 真实试读操作细则

1. 找 3 名不懂人类图的普通人（家人 / 同事 / 朋友即可，不要找熟悉本项目的人）。
2. 给每人随机 10 条改写后的释义，**不要解释人类图背景**。
3. 请他们用自己的话复述："这条在说我什么？我该留意什么？"
4. 能复述出"具体场景 + 自己的反应"算理解；只复述抽象词（"说我很有能量"）算未理解。
5. 每人 ≥3/10 理解 → 通过；否则打回，且把未理解的原文条目列为重点重改对象。

### 4.2 验证流程（每批都走一遍）

```
改写提交 → L1 自动扫描 → L2 盲审 → L3 试读 → 批次验收 → 从基线快照删除已达标条目
   ↑                                                        │
   └──────────────── 不达标：打回 ───────────────────────────┘
```

1. **提交**：每批改完，提交到分支 `dev/DEV-702-batch-N`，附本批清单（改了哪些条目 ID）。
2. **L1**：CI 跑 `npm test`；不过直接打回，不进 L2。
3. **L2**：生成盲审包，两名评审独立打分，产出打分表。
4. **L3**：3 名试读者试读，产出试读记录。
5. **判定**：三级全过 → 验收，从基线快照删条目；任一级不过 → 按 §5 打回。
6. **报告**：每批产出 `docs/VERIFY-v3.8.0-批次N.md`，记录达标率与不达标清单。

### 4.3 分批策略（避免一次性改 524 条失控）

| 批次 | 内容 | 条数 | 优先级 | 理由 |
| --- | --- | --- | --- | --- |
| 批次 1 | `gateInsight.ts` 4 字段（达标率 11%，最低） | 256 | P0 | 数量最大、最难，先啃 |
| 批次 2 | `destinyText.ts` 人生轨迹（达标率 5%，最低） | 19 | P0 | 量小、用户最常读 |
| 批次 3 | `interpretations.ts` GATE_TEXT | 128 | P1 | 核心释义，用户点开必看 |
| 批次 4 | CHANNEL_TEXT + CENTER_TEXT + TYPE/AUTHORITY | 66 | P1 | 中等量 |
| 批次 5 | `typeDetail.ts` + 剩余 | 55 | P2 | 已较好（35%），收尾 |

> 每批独立走完三级验证，**前一批未验收不得开始下一批**（防止欠账累积）。

## 5. 不达标打回机制（用户明确要求的核心）

### 5.1 打回触发条件（任一命中即打回）

| 触发 | 判定来源 | 打回范围 |
| --- | --- | --- |
| L1 机械不达标 ≥1 条 | `readability.test.ts` | 该条所在批次全部 |
| L2 盲审达标率 <90% | 盲审打分表 | 该批次全部（不只不合格条目） |
| L2 出现"完全看不懂"条目 ≥1 | 盲审打分表 | 该条目 + 同类条目 |
| L3 试读每人理解 <3/10 | 试读记录 | 该批次全部 |
| 条目数减少（靠删条目达标） | L1 检查 | 立即打回，恢复条目 |

### 5.2 打回单模板（每次打回必填）

```markdown
## 打回单 · 批次 N · 第 R 轮
- 打回关卡：L1 / L2 / L3
- 触发条件：（引用上表具体项 + 数值）
- 不达标条目清单：
  | 条目 ID | 原文 | 不达标原因 | 修改方向建议 |
  | --- | --- | --- | --- |
  | G57.defined | "闸门 57 给你直觉…" | 编号当主语 + 无场景 | 改成"你常突然觉得不对…（闸门 57）" |
- 共性问题：（如"256 条 gateInsight 普遍只有体感没有场合"）
- 重改要求：仅限上述条目 + 同类条目，不得扩大改动范围
- 重改截止：下一迭代日前
```

### 5.3 轮次上限与升级规则

| 轮次 | 处理 |
| --- | --- |
| 第 1 轮不达标 | 按打回单重改，走完整三级验证 |
| 第 2 轮不达标 | 产品 owner 介入，评审"修改方向是否有误"；调整框架后重改 |
| **第 3 轮仍不达标** | **停止迭代**，升级给你决策：①放宽该条标准并登记例外 ②换改写策略 ③接受该条目保留原文并在文档标注 |
| 任一轮出现"内核被改动" | 立即停止，回滚，不属于本迭代范围 |

> **为什么设 3 轮上限**：避免无限打回拖死项目；3 轮还不行说明是框架问题或素材本身不适合白话化，需要你拍板，不是执行层能解决的。

### 5.4 防"应试式改写"

- L2 盲审的评审者必须含 1 名不懂人类图的人——懂的人会自动脑补，看不出"看不懂"。
- L3 试读者不得获得任何背景解释——否则测的是"解释得好"而不是"文本本身清楚"。
- 场景锚点不得堆砌凑数：一句话塞 3 个锚点但语义不通，L2 会判"不绕"不达标。
