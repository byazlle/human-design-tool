# 人类图（Human Design）桌面端计算应用 · 技术文档

## 1. 项目概述

### 1.1 项目背景与目标

人类图（Human Design）是一套融合了西洋占星、中国易经（六十四卦）、卡巴拉生命之树与印度脉轮系统的自我认知体系。它以个人精确的出生时刻、出生地点为输入，通过天体力学计算，生成一张包含类型（Type）、内在权威（Inner Authority）、策略（Strategy）、九个能量中心（Centers）、六十四闸门（Gates）与三十六通道（Channels）的"人体图"（BodyGraph）。

本项目目标是开发一款**桌面端**人类图计算应用，面向中文普通用户与爱好者，提供：

- 便捷的输入方式：支持通过中国大陆居民身份证号码自动提取出生日期与地区，也支持手动填写出生日期、精确出生时间与出生地点；
- 严谨的计算内核：基于天文星历（Ephemeris）与固定映射规则，本地计算并生成完整的人类图要素；
- 直观的结果呈现：以图形化 BodyGraph 与结构化文字报告双重形式展示；
- 隐私优先：所有敏感身份信息（身份证号、出生时间）**仅在本地设备处理，不上传任何服务器**。

### 1.2 文档范围

本文档覆盖从立项到交付的完整技术设计，包含：可行性分析、系统总体架构、核心功能模块、人类图计算的数据与算法逻辑、用户输入与校验规则、技术选型建议、开发实施与部署方案。本文档不涉及市场运营方案与具体 UI 视觉稿（另行产出）。

## 2. 项目可行性分析

### 2.1 技术可行性

人类图的计算本质是一组确定的数学与天文运算，不存在不可克服的技术障碍：

- **天文历计算**：行星黄经计算已有成熟开源方案（Swiss Ephemeris、astronomy-engine），精度可达角秒级，远超人类图所需的 0.1° 级别；
- **闸门映射**：是黄道经度到 64 卦的固定线性映射（每卦 5.625°），纯几何运算；
- **类型/权威/策略判定**：是一组基于"已定义通道 → 已定义中心 → 类型"的确定性规则树；
- **桌面端框架**：Electron 与 Tauri 均已广泛用于生产级桌面应用，跨平台（Windows / macOS / Linux）打包成熟；
- **图形渲染**：BodyGraph 为固定拓扑图，使用 Canvas 或 SVG 即可精确绘制。

综上，技术可行性高，核心难点在于"计算精度对齐权威实现"与"身份证地区码到经纬度的映射"，而非算法本身。

### 2.2 用户与业务可行性

- 人类图在中文互联网（小红书、微信社群、知识付费）具备稳定受众，用户对"一键生成自己的图"有强需求；
- 桌面端相比网页端优势在于：可离线运行、隐私数据不出本机、可作为长期本地工具沉淀；
- 区别于竞品（多为网页端且需联网提交生日），本应用的"本地优先 + 身份证快捷录入"构成差异化卖点。

### 2.3 法律与合规可行性

身份证号属于《个人信息保护法》（PIPL）定义的敏感个人信息。本项目必须遵循：

- **本地优先处理**：身份证号仅在本机内存/临时态中使用，绝不通过任何网络通道上传；
- **最小提取原则**：系统只提取"出生日期"与"地区代码"两个派生字段，原始身份证号不持久化存储，不写入日志，不写入导出报告；
- **明示同意**：在身份证输入处提供隐私说明与勾选同意；
- **脱敏展示**：若需回显，仅展示前 6 位 + `********` + 末位；
- **数据留存**：用户报告以匿名方式（不含证件号）本地保存，便于复看。

> 注：本项目为本地计算工具，不涉及对外提供身份证核验服务，不构成《身份证法》意义上的"查验/扣押"场景，但仍须遵守 PIPL 对敏感个人信息的处理规则。

### 2.4 经济与资源可行性

- 无需服务器端算力与带宽成本（纯本地）；
- 主要成本集中于研发人力与测试比对（需购买/获取权威人类图软件的对照样本）；
- 可采用一次性买断或免费+增值（如高级报告、批量导出）的商业模式，边际成本低。

### 2.5 可行性结论

项目在技术上可落地、合规上可控、商业上具备差异化空间，建议进入开发实施阶段。主要风险点（按优先级）为：① 计算精度需用权威实现比对校准；② 身份证地区码需维护一份 GB/T 2260 到经纬度的映射库；③ 出生时间精度直接影响结果，需在 UX 上强提示。

## 3. 系统总体架构设计

### 3.1 架构风格

采用**分层 + 模块化**的桌面端架构，整体划分为表现层、业务编排层、计算引擎层、数据层四层，层间通过明确定义的接口通信，保证计算内核可独立测试与替换。

### 3.2 逻辑分层

```
┌─────────────────────────────────────────────┐
│  表现层 (UI Layer)                            │
│  - 输入表单（身份证/手动）  - BodyGraph 画布   │
│  - 报告视图  - 设置与隐私中心                  │
└───────────────┬─────────────────────────────┘
                │  领域事件 / 命令
┌───────────────▼─────────────────────────────┐
│  业务编排层 (Application/Orchestration)        │
│  - 输入聚合  - 校验调度  - 计算任务编排         │
│  - 结果组装  - 报告生成                        │
└───────────────┬─────────────────────────────┘
                │  纯函数调用
┌───────────────▼─────────────────────────────┐
│  计算引擎层 (Human Design Engine)              │
│  - 时间归一化  - 星历计算  - 设计/人格双算      │
│  - 闸门/线路映射  - 中心/通道判定  - 类型权威   │
└───────────────┬─────────────────────────────┘
                │  查询
┌───────────────▼─────────────────────────────┐
│  数据层 (Data Layer)                           │
│  - 地区码↔经纬度库  - 闸门/通道定义表          │
│  - 本地用户报告存储 (SQLite)                   │
└─────────────────────────────────────────────┘
```

### 3.3 部署形态

以单一桌面安装包（`.exe` / `.dmg` / `.AppImage`）形式分发，应用内所有计算与存储均在本机完成。无后端服务，无账号体系（可选本地密码锁）。

### 3.4 关键数据流

```
用户输入(身份证/手动)
   → 输入模块提取 {出生日期, 地区码, 出生时间, 出生地点}
   → 校验模块(格式/合法性/范围)
   → 地理模块(地区码/地点 → 经纬度 + 时区 + 夏令时)
   → 时间模块(本地时间 → UTC → 儒略日)
   → 星历模块(UTC + 经纬度 → 各行星黄经/赤纬)
   → 双算模块(人格=出生时刻; 设计=前约88°太阳弧)
   → 映射模块(黄经 → 闸门Gate + 线路Line)
   → 判定模块(通道 → 中心定义 → 类型/权威/策略/人生角色/定义型)
   → 渲染模块(BodyGraph 图形 + 文字报告)
   → 展示/导出模块
```

### 3.5 技术约束

- 计算引擎必须是**纯函数、无副作用、可确定性复现**（相同输入恒定相同输出）；
- 所有时间处理统一以 UTC 为内部基准，仅在展示层转回本地时区；
- 星历数据文件（如 Swiss Ephemeris 星表）随包分发，避免运行时联网。

## 4. 核心功能模块划分

### 4.1 输入模块（Input Module）

- **身份证录入子模块**：解析 18 位身份证，提取出生日期与地区码；
- **手动录入子模块**：提供日期选择器、时间输入（时/分/秒）、地点搜索框；
- **输入聚合**：统一产出标准化输入对象 `BirthInput { date, time, place }`。

### 4.2 校验模块（Validation Module）

- 身份证格式与校验码校验（见第 6 章）；
- 出生日期合法性（年份范围、闰年、月份天数）；
- 出生时间范围（00:00:00–23:59:59）与时区一致性；
- 出生地点可解析性（能否映射到经纬度）。

### 4.3 天文历计算引擎（Ephemeris Engine）

- 输入 UTC 时刻与经纬度，输出各天体（太阳、地球、月亮、北交点、水星、金星、火星、木星、土星、天王星、海王星、冥王星）的黄道经度与赤纬；
- 提供"按儒略日查询行星位置"的纯函数接口。

### 4.4 人类图计算核心（HD Core）

- 双算（设计/人格）；
- 闸门与线路映射；
- 中心/通道定义判定；
- 类型、内在权威、策略、人生角色、定义型判定；
- 输出标准化的 `HumanDesignChart` 领域对象。

### 4.5 图形渲染模块（BodyGraph Renderer）

- 按固定拓扑绘制九中心、三十六通道；
- 依据计算结果填充"已定义"（着色）与"未定义"（留白）状态；
- 标注激活的闸门编号与线路；
- 支持 SVG 矢量导出与 PNG 位图导出。

### 4.6 报告与导出模块（Report Module）

- 生成结构化文字报告（类型解读、权威说明、各中心/闸门释义）；
- 支持导出 PDF / 图片 / 纯文本摘要；
- 导出内容**不含**身份证号等敏感字段。

### 4.7 本地存储模块（Storage Module）

- 以 SQLite 保存匿名化的历史报告（仅含图表要素与展示用日期）；
- 不存储身份证号、原始出生时间等可回溯到个人的敏感信息（除非用户主动开启并加密）。

## 5. 人类图计算的数据与算法逻辑

### 5.1 输入数据规格

计算所需的最小数据集：

| 字段 | 类型 | 精度要求 | 说明 |
|------|------|----------|------|
| 出生日期 | Date | 年/月/日 | 来自身份证或手动 |
| 出生时间 | Time | 建议到秒，至少到分 | 时间精度直接影响结果，误差 4 分钟约影响通道判定 |
| 出生地点 | 文本/坐标 | 经纬度到 0.01° | 决定时区、夏令时与天体视位置 |
| 时区 | 派生 | — | 由地点+日期推导 |

### 5.2 时间归一化

1. 将本地出生时间按"地点所在时区 + 当日是否处于夏令时"转换为 UTC；
2. 由 UTC 计算**儒略日（Julian Day, JD）**连续计时，避免历法边界问题；
3. 内部所有星历查询均以 JD（UTC）为入参。

### 5.3 经纬度、时区与夏令时

- 地点 → 经纬度：手动输入用内置"城市/地名 → 经纬度"库（如 GeoNames 精简版）匹配；身份证地区码映射到该地区代表城市的经纬度；
- 时区：由经纬度 + 日期查"时区边界数据库"（如 Time Zone Boundary Builder）得到 IANA 时区，再结合历史夏令时规则得出 UTC 偏移；
- 夏令时：必须按出生年份的历史规则计算（例如中国已于 1991 年停用夏令时），不可简单套用当前规则。

### 5.4 行星位置计算

以 Swiss Ephemeris 或 astronomy-engine 计算给定 JD（UTC）下各天体的**黄道经度（ecliptic longitude, 0°–360°）**：

- 太阳：直接由星历给出；
- 地球：人类图中"地球"位置取太阳经度 + 180°（即太阳的对立面）；
- 北交点：月亮轨道升交点；南交点取北交点 + 180°；
- 其余行星（月、水、金、火、木、土、天、海、冥）：由星历给出。

> 人类图标准参与计算的"天体位置"共 12 个：太阳、地球、月亮、北交点、水星、金星、火星、木星、土星、天王星、海王星、冥王星。

### 5.5 设计（Design）与人格（Personality）双算

人类图对每个天体计算**两套**位置：

- **人格（Personality / 意识）**：取精确出生时刻的行星位置；
- **设计（Design / 形式）**：取出生时刻前"约 88° 太阳黄经弧"对应的时刻的行星位置。

具体做法：以出生时刻太阳黄经为基准，向前回溯至太阳黄经减少 88° 的时刻（因太阳约每天移动 1°，约对应出生前 88 个日历日，精确值需按当年太阳运动速率迭代求解），在该回溯时刻重新计算全部 12 个天体的位置，即为设计位置。

> 设计维度代表"身体的设计/遗传形式"，人格维度代表"心智与意识"，两者叠加形成完整图表。

### 5.6 闸门（Gate）映射

将黄道 360° 等分为 64 段，每段 5.625°，对应一个闸门（对应《易经》六十四卦，按文王卦序编号）：

```
gate_index = floor( (longitude mod 360) / 5.625 ) + 1      // 闸门编号 1–64
```

人类图约定**闸门 1 起于白羊座 0°**，依黄道顺序依次排列至闸门 64。

### 5.7 线路（Line）映射

每个闸门内部再均分为 6 条线路（对应卦之六爻），每条 0.9375°：

```
line_index = floor( ( (longitude mod 360) mod 5.625 ) / 0.9375 ) + 1   // 线路 1–6
```

> 进阶层（颜色 Color 1–6、色调 Tone 1–6、碱基 Base 1–64）由更细经纬度划分决定，属精细化变量，基础图表可仅输出闸门+线路；本文档算法层保留扩展接口。

### 5.8 能量中心（Center）定义判定

人类图有九个中心。判定规则：

- **通道（Channel）定义**：若一条通道的**两端闸门同时被激活**（该闸门在设计或人格任一维度出现），则该通道为"已定义"；
- **中心定义**：若一个中心通过至少一条"已定义通道"与另一中心相连，则该中心为"已定义"（着色）；
- 仅含"悬挂闸门"（激活但两端未同时激活）的中心仍为"未定义/开放"，但该闸门仍参与变量计算。

九个中心与连接关系（拓扑固定）：头—眉心、眉心—喉咙、G—喉咙、心(意志)—喉咙、情绪—喉咙、骶骨—G(部分经喉咙)、脾—喉咙、根—脾脏/情绪/意志等，共 36 条固定通道。

### 5.9 通道（Channel）判定

遍历 36 条预定义通道，对每条通道检查其两个端点闸门是否在"设计+人格"合计的激活闸门集合中成对出现。成对出现即标记该通道已定义，并据此点亮两端中心。

### 5.10 类型（Type）判定规则

按以下优先级判定（需结合"已定义中心与已定义通道"拓扑）：

1. **反映者（Reflector）**：九个中心全部未定义（无任何已定义通道）→ 唯一全开放类型；
2. **显示者（Manifestor）**：存在一个"动力中心"（根、骶骨、情绪、心/意志）经已定义通道直连喉咙，且**骶骨未**经已定义通道连到喉咙；
3. **生产者（Generator）**：骶骨经已定义通道连到喉咙，且无其他动力中心直连喉咙；
4. **显生者（Manifesting Generator）**：骶骨连喉咙，且另有至少一个动力中心经已定义通道直连喉咙（兼具"显示"属性）；
5. **投射者（Projector）**：无已定义骶骨，但至少有一个已定义中心经通道连到喉咙（可"引导"能量）。

> 上述为业界通用判定逻辑；正式实现须以权威 BodyGraph 规范逐条比对校准。

### 5.11 内在权威（Inner Authority）判定规则

权威由"哪个中心被定义"决定，按以下优先级取首个命中：

1. 情绪中心（Solar Plexus）已定义 → **情绪权威**（需情绪清晰的"波动"中决策）；
2. 骶骨（Sacral）已定义且无情绪权威 → **骶骨权威**（感应式回应）；
3. 心/意志（Heart/Ego）已定义 → **自我权威（Ego）**；
4. 脾脏（Spleen）已定义 → **脾脏权威**（瞬间直觉）；
5. G 中心（Identity）已定义 → **自我投射权威（Self-Projected）**；
6. 以上皆无 → 显示者为**环境/无权威**，反映者为**月亮权威（Lunar）**。

### 5.12 策略（Strategy）映射

| 类型 | 策略 |
|------|------|
| 显示者 | 行动前告知（Inform） |
| 生产者 | 等待回应（Wait to Respond） |
| 显生者 | 等待回应，再告知（Respond then Inform） |
| 投射者 | 等待邀请（Wait for the Invitation） |
| 反映者 | 等待一个 lunar cycle（约 28 天） |

### 5.13 人生角色（Profile）判定

人生角色由两个"太阳线路"组合而成，记作 `X/Y`：

- **X（意识/人格太阳线路）**：人格维度太阳所在线路（1–6）；
- **Y（潜意识/设计太阳线路）**：设计维度太阳所在线路（1–6）。

组合共形成 12 种人生角色：1/3、1/4、2/4、2/5、3/5、3/6、4/1、4/6、5/1、5/2、6/2、6/3。

### 5.14 定义型（Definition）判定

依据"已定义中心被分割成几个互不连通的集团"判定：

- 全部连通为一团 → **单一定义（Single Definition）**；
- 分成 2 / 3 / 4 团 → **双分 / 三分 / 四分定义（Split / Triple Split / Quadruple Split）**；
- 无定义（反映者）→ **无定义（No Definition）**。

### 5.15 算法汇总（伪代码）

```
function computeHumanDesign(birthInput):
    utc        = toUTC(birthInput.date, birthInput.time, tzOf(birthInput.place))
    jdPerson   = julianDay(utc)
    jdDesign   = designJulianDay(jdPerson)          // 回溯约 88° 太阳弧
    planetsP   = ephemeris(jdPerson, latlon)        // 人格 12 天体黄经
    planetsD   = ephemeris(jdDesign, latlon)        // 设计 12 天体黄经
    gatesP     = mapGates(planetsP)                 // 闸门+线路
    gatesD     = mapGates(planetsD)
    activations = union(gatesP, gatesD)             // 激活闸门集合
    channels   = defineChannels(activations)         // 36 选已定义
    centers    = defineCenters(channels)             // 9 中心定义态
    type       = decideType(centers, channels)
    authority  = decideAuthority(centers)
    strategy   = mapStrategy(type)
    profile    = decideProfile(gatesP.sun.line, gatesD.sun.line)
    definition = decideDefinition(centers, channels)
    return HumanDesignChart(type, authority, strategy,
                            centers, channels, activations,
                            profile, definition)
```

## 6. 用户输入与校验规则

### 6.1 身份证号码结构（GB 11643-1999，18 位）

| 位段 | 长度 | 含义 |
|------|------|------|
| 1–6 位 | 6 | 地址码（省 2 + 市 2 + 县 2，依据 GB/T 2260） |
| 7–14 位 | 8 | 出生日期（YYYYMMDD） |
| 15–17 位 | 3 | 顺序码（同一地区同日生序号；**第 17 位奇数为男、偶数为女**） |
| 18 位 | 1 | 校验码（0–9 或 X，ISO 7064 MOD 11-2） |

> 关键限制：身份证**只含出生日期，不含出生时间**。因此即便使用身份证录入，精确的出生时间仍需用户手动填写；同时地区码仅指示行政区，须映射为代表城市经纬度，并允许用户校正精确出生地点。

### 6.2 身份证校验码算法

对前 17 位数字，按权重 `W = [7,9,10,5,8,4,2,1,6,3,7,9,10,5,8,4,2]` 加权求和，再模 11 映射：

```
S = Σ ( digit[i] × W[i] )            i = 0..16
mod = S mod 11
checkMap = ['1','0','X','9','8','7','6','5','4','3','2']
校验码 = checkMap[mod]
```

校验码与第 18 位（不区分大小写，X 记作大写）一致方为合法。

### 6.3 地区码映射（GB/T 2260）

- 前 2 位 = 省级（如 11=北京，31=上海，44=广东）；
- 中间 2 位 = 地级市；
- 末 2 位 = 区县；
- 应用内部维护一份"地区码 → 代表城市名 + 经纬度 + 默认时区"的映射表；
- 仅用于**自动预填**出生地区与近似坐标，最终坐标以用户确认的"出生地点"为准。

### 6.4 手动输入字段与格式

| 字段 | 格式 | 示例 | 备注 |
|------|------|------|------|
| 出生日期 | YYYY-MM-DD | 1990-05-21 | 需校验合法性 |
| 出生时间 | HH:MM[:SS] | 14:30:00 | 建议到秒 |
| 出生地点 | 自由文本 | 广东省深圳市南山区 | 用于检索经纬度 |

### 6.5 出生时间精度要求

- 最低要求：精确到分钟；
- 推荐：精确到秒（部分通道判定对 4 分钟级误差敏感）；
- UX 强提示：明确告知用户"时间每偏差约 4 分钟，可能导致闸门/通道变化"。

### 6.6 出生地点 → 坐标库

- 内置"城市/地名 → 经纬度 + 时区"数据库（随包分发，可离线）；
- 支持模糊搜索与用户手动微调坐标；
- 经纬度精度建议 ≥ 0.01°，以满足时区与天体视位置需求。

### 6.7 时区与夏令时校验

- 根据地点经纬度与出生日期推导 IANA 时区；
- 应用历史夏令时规则（不同国家/年份不同），避免用当前规则反推历史时刻；
- 对"临界时刻"（接近夏令时切换点）给出提示，建议用户核实。

### 6.8 错误码与提示文案（示例）

| 错误码 | 触发条件 | 用户提示 |
|--------|----------|----------|
| E1001 | 身份证位数非 18 | 请输入 18 位居民身份证号码 |
| E1002 | 校验码不符 | 身份证校验失败，请核对号码 |
| E1003 | 地区码无匹配 | 无法识别地区，请手动选择出生地 |
| E2001 | 出生日期非法 | 出生日期不正确（如 2 月 30 日） |
| E2002 | 出生时间格式错 | 请按 时:分:秒 格式填写 |
| E3001 | 地点无法定位 | 未找到该地点坐标，请更精确或手动标注 |

## 7. 技术选型建议

### 7.1 桌面框架对比

| 维度 | Electron | Tauri |
|------|----------|-------|
| 技术栈 | Chromium + Node.js | Rust + 系统 WebView |
| 包体积 | 大（~100MB+） | 小（~10MB） |
| 性能/内存 | 较高占用 | 轻量 |
| 生态成熟度 | 极高 | 高且增长快 |
| 适合场景 | 富交互、快速迭代 | 轻量、隐私敏感、体积小 |

**建议**：若团队熟悉 Web 技术且追求开发速度选 Electron；若重视体积小、资源占用低、安全边界清晰，选 Tauri。两者均可承载本应用。本文档后续示例以"Web 技术栈（TypeScript）+ 计算内核可独立"为前提。

### 7.2 计算内核语言

- 核心计算建议用 **TypeScript（与 UI 同栈，便于统一测试）** 或 **Rust/Go（性能与确定性更佳，经 WASM/FFI 调用）**；
- 关键：计算内核必须是纯函数、可单测、可脱离 UI 运行。

### 7.3 天文历库

| 库 | 语言 | 精度 | 许可 |
|----|------|------|------|
| Swiss Ephemeris | C（多语言绑定） | 极高（角秒级） | 商业需授权/个人免费 |
| astronomy-engine | TS/Python/… | 高（满足需求） | MIT（友好） |

**建议**：优先评估 `astronomy-engine`（MIT、易嵌入、精度足够）；若需与权威实现逐点比对，可引入 Swiss Ephemeris 作交叉验证基准。

### 7.4 图形渲染

- **SVG**：矢量、可缩放、易导出、易标注，推荐用于 BodyGraph；
- **Canvas**：高性能，适合复杂动画；本应用为静态图，非必需。

### 7.5 本地存储

- 历史报告用 **SQLite**（轻量、单文件、易备份）；
- 敏感字段（身份证号、精确时间）默认不入库，或加密存储（用户主动开启 + 本地密钥）。

### 7.6 地区码与坐标数据

- 地区码：内置 GB/T 2260 精简映射表（省/市/县 → 代表城市）；
- 坐标：内置城市级经纬度 + 时区库（如随包分发精简 GeoNames）。

### 7.7 安全与隐私

- 全程本地计算，禁用任何遥测上传出生信息；
- 身份证号仅存于输入控件内存，关闭/提交后立即清除；
- 导出报告自动剔除证件号与精确时间的可回溯字段；
- 提供"清空本地数据"一键功能。

### 7.8 选型结论表

| 关注点 | 推荐方案 |
|--------|----------|
| 桌面框架 | Tauri（轻量/隐私优先）或 Electron（开发快） |
| 计算内核 | TypeScript 纯函数模块（或 Rust→WASM） |
| 星历 | astronomy-engine（MIT），Swiss Ephemeris 作比对基准 |
| 渲染 | SVG |
| 存储 | SQLite（匿名化） |
| 数据 | 内置 GB/T 2260 + 城市经纬度/时区库 |

## 8. 开发实施与部署方案

### 8.1 开发阶段划分（里程碑）

| 阶段 | 周期(估) | 交付物 |
|------|----------|--------|
| M1 内核原型 | 3 周 | 计算内核（时间/星历/闸门/类型）纯函数 + 单元测试 |
| M2 精度校准 | 2 周 | 与权威实现比对报告（抽样 ≥200 例，误差归零） |
| M3 桌面壳 + 输入 | 3 周 | 可运行桌面应用，含身份证/手动输入与校验 |
| M4 图形与报告 | 3 周 | BodyGraph 渲染 + 文字报告 + 导出 |
| M5 隐私与存储 | 1.5 周 | 本地存储、脱敏、清空功能 |
| M6 打包与发布 | 1.5 周 | 签名安装包、自动更新、使用文档 |

### 8.2 团队与角色

- 算法工程师 ×1（星历/人类图内核）；
- 前端/桌面工程师 ×1–2（UI、渲染、打包）；
- 测试工程师 ×1（精度比对、回归）；
- 可选：领域顾问 ×1（人类图释义内容审核）。

### 8.3 测试策略

- **单元测试**：内核每个函数（闸门映射、类型判定等）覆盖边界用例；
- **集成测试**：端到端"输入 → 图表"链路；
- **精度比对测试**：以权威人类图软件输出为基线，抽样比对类型/权威/闸门一致性；
- **UI 测试**：输入校验、错误提示、报告展示；
- **隐私测试**：验证身份证号不上网、不落盘。

### 8.4 精度验证方法

1. 收集 ≥200 条已知生日（含跨时区、夏令时边界、闰年等异常样本）；
2. 用本应用与权威实现分别生成图表；
3. 逐字段比对：闸门集合、通道集合、类型、权威、人生角色、定义型；
4. 差异项定位到具体算法环节并修正，直至完全一致。

### 8.5 打包与分发

- Windows：NSIS/Inno 安装包，EV 代码签名（消除 SmartScreen 警告）；
- macOS：公证（Notarization）+ 开发者签名；
- Linux：AppImage / deb；
- 内置星历与数据文件随包分发，首次启动无需联网；
- 提供增量自动更新（仅更新应用本体，用户数据不受影响）。

### 8.6 部署与运维

- 纯客户端，无服务端运维；
- 提供版本内"检查更新"与"数据导出/清空"；
- 建立最小反馈渠道（本地日志导出 + 手动上报，且上报内容默认不含个人信息）。

### 8.7 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 计算精度偏差 | 图表错误 | 权威实现比对校准（M2） |
| 地区码/时区数据过时 | 坐标/时区错 | 定期更新内置库 |
| 出生时间不准 | 结果漂移 | UX 强提示 + 提供"时间容差"说明 |
| 隐私合规 | 法律风险 | 本地优先 + 脱敏 + 明示同意 |
